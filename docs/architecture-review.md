# 우리 사이 구조 검토와 개선 계획

검토일: 2026-09-27

검토 기준: `8f6ac40` (`main`)

구현 상태 갱신: 2026-09-27. 아래 항목 중 R1, R2, R5, R7은 코드 수정이 반영되었지만, Firebase Emulator·운영 규칙·두 계정 동작 검증까지 끝난 것은 아니다.

## 먼저 수정할 사항

우선순위는 P1(실제 사용자 초대 전 해결), P2(다음 개발 단계에서 해결)로 구분한다. 아래 내용은 저장소의 코드와 규칙을 정적으로 검토한 결과다. 운영 Firebase의 현재 설정이나 실제 데이터 노출을 확인한 결과는 아니다.

### R1. [P1] 이메일 소유 확인 없이 그룹 초대에 접근할 수 있음

근거: `firestore.rules:14`, `firestore.rules:110`, `firestore.rules:121`, `firestore.rules:141`, `PrivateCircle/AuthView.swift:38`.

초대 조회·수락과 그룹 가입 규칙은 토큰의 이메일 문자열만 비교한다. 회원가입에는 이메일 확인 메일 발송 및 확인 대기 과정이 없다. 아직 가입하지 않은 초대 대상자의 이메일로 다른 사람이 계정을 만들 수 있는 경우, 해당 이메일을 실제로 소유하지 않아도 저장소의 규칙상 초대를 조회하고 수락할 수 있다.

수정: 이메일 확인 화면, 재발송, 확인 후 사용자 정보·토큰 갱신을 구현한다. 이메일을 근거로 권한을 부여하는 초대 조회·수락·멤버 생성 경로 모두에 확인된 이메일 조건을 적용한다. 화면에서만 막아서는 안 된다. 이미 가입한 사용자를 위한 확인 안내도 포함한다.

진행: `AuthView`에 가입 후 인증 메일, 재발송, 인증 상태 재확인을 추가했고, `firestore.rules`의 그룹·초대·모임 권한에 확인된 이메일 조건을 추가했다. 운영 Firebase에 규칙을 배포하지 않았고 Emulator 검증도 아직 없으므로 완료로 보지 않는다.

완료 기준: 미확인 이메일 계정의 초대 조회와 수락은 거절되고, 확인된 수신자만 원자적으로 가입한다. 다른 이메일과 비로그인 요청도 거절된다. Firebase는 이메일 문자열과 소유 확인 여부를 별도 토큰 필드로 제공한다. [Firebase 인증과 규칙](https://firebase.google.com/docs/rules/rules-and-auth), [이메일 확인 API](https://firebase.google.com/docs/auth/ios/manage-users#send_a_user_a_verification_email).

### R2. [P1] 계정 전환 시 이전 계정의 메모리 상태와 비동기 결과가 남을 수 있음

근거: `PrivateCircle/ContentView.swift:5`, `PrivateCircle/ContentView.swift:119`, `PrivateCircle/MeetupFeature.swift:14`, `PrivateCircle/MeetupFeature.swift:26`, `PrivateCircle/MeetupFeature.swift:89`.

모임 저장소는 로그인 화면 바깥의 `ContentView`가 계속 소유한다. 로그아웃 시 초기화되지 않고, 다음 사용자의 조회가 시작될 때에만 목록을 비운다. 조회·생성이 끝난 뒤 현재 사용자나 요청 세대를 확인하는 코드도 없다. A 계정의 작업이 지연되는 동안 B 계정으로 바꾸면 이전 데이터가 잠깐 표시되거나 늦게 끝난 결과가 새 화면 상태를 덮을 여지가 있다. 이는 로컬 화면 상태의 계정 격리 문제이며, Firestore의 사용자별 경로 제한을 우회한다는 의미는 아니다.

수정: 로그인한 UID에 귀속된 화면과 저장소 수명을 만든다. 로그아웃·계정 변경 시 목록, 오류, 선택 상태, 진행 중 작업을 정리한다. 모든 비동기 완료 지점에서 UID 및 요청 세대를 검증하고 취소된 작업의 결과는 반영하지 않는다. 앞으로 추가할 실시간 구독도 같은 경계에서 해제한다.

진행: `MeetupStore`를 인증 화면 바깥의 전역 상태에서 로그인 사용자 탭 화면 안으로 옮겼다. 사용자 ID로 화면을 식별하고, 모임 조회마다 요청 세대·사용자 ID·취소 여부를 검사한다. 지연 응답을 주입하는 계정 전환 검증은 아직 없다.

완료 기준: A의 읽기·쓰기 응답을 지연시킨 뒤 B로 로그인해도 A의 데이터와 오류가 B 화면에 반영되지 않는다. 로그아웃 직후 개인 데이터가 메모리 화면 상태에서 제거된다.

### R3. [P2] 회원가입 중 일부 단계가 실패해도 앱에 진입할 수 있음

근거: `PrivateCircle/AuthView.swift:19`, `PrivateCircle/AuthView.swift:38`, `PrivateCircle/ContentView.swift:30`.

회원가입은 Auth 계정 생성, 이름 갱신, Firestore 프로필 저장을 차례대로 수행한다. 반면 인증 리스너는 로그인 상태가 생기면 바로 `user`를 설정한다. 프로필 저장 전 홈으로 전환될 수 있고, 뒤 단계가 실패해도 계정은 이미 생성되어 있다. 이후 로그인에서 누락된 프로필을 복구하는 경로도 없다.

수정: 로그인 여부와 가입 준비 완료 여부를 나눈다. 인증 확인·프로필 준비·정상 이용·복구 필요 상태를 명시하고, 가입을 다시 시도할 때 기존 계정을 재생성하지 않고 누락된 단계를 이어 간다. 로그아웃 실패도 `try?`로 숨기지 않고 처리한다.

완료 기준: Auth 생성 후 프로필 저장 실패를 주입해도 복구 화면으로 이동하며, 재시도로 정상 상태에 도달한다. Firebase의 계정 생성 성공 시 자동 로그인 동작은 [공식 문서](https://firebase.google.com/docs/auth/ios/password-auth#create_a_password-based_account)에 명시되어 있다.

### R4. [P2] 같은 그룹의 중복 초대가 처리 불가능한 상태로 남음

근거: `PrivateCircle/GroupsView.swift:114`, `PrivateCircle/GroupsView.swift:125`, `firestore.rules:44`, `firestore.rules:116`.

초대마다 새 문서를 만들기 때문에 같은 그룹·이메일로 여러 초대를 보낼 수 있다. 첫 초대를 수락하면 멤버와 내 그룹 문서가 생긴다. 이후 초대 수락은 동일 문서를 다시 쓰는 작업이 되지만 규칙은 갱신을 거절하므로 실패한다. 남은 초대를 거절하거나 취소하는 기능도 없다.

수정: 활성 초대의 중복 방지, 이미 가입한 경우의 멱등 처리, 수신자의 거절과 발신자의 취소를 정의한다. 멤버 갱신을 무조건 허용하는 방식으로 해결하지 않는다. 초대 상태·멤버십·내 그룹 목록의 일관성을 유지한다.

완료 기준: 같은 사람에게 두 번 초대하고 한 번 가입해도 처리 불가능한 초대가 남지 않는다. 재시도와 동시 수락이 권한 변경이나 중복 가입을 만들지 않는다.

### R5. [P2] 일반 이용 화면에 샘플 친구와 추억이 실제 기록처럼 표시됨

근거: `PrivateCircle/ContentView.swift:226`, `PrivateCircle/ContentView.swift:235`, `PrivateCircle/HomeView.swift:10`, `PrivateCircle/HomeView.swift:47`, `PrivateCircle/MeetupFeature.swift:264`.

홈·친구·추억은 일반 로그인에서도 `MockData`를 사용한다. 새 계정에도 모르는 친구 이름, 함께한 활동, 사진 수가 나타난다. 모임 작성 시트에는 샘플 안내가 있지만 나머지 화면에는 같은 구분이 없다.

수정: 일반 화면에는 실제 데이터 또는 빈 상태를 전달한다. 샘플 공급과 작성 시트 자동 채움은 Debug 미리보기 경계로 모은다. 모임 참여자는 실제 그룹 구성원으로 전환한다.

진행: 일반 홈·친구·추억 화면에서 샘플 친구와 추억을 제거하고 빈 상태를 표시한다. 실제 그룹 상세에서 그룹 UID를 사용해 공동 모임을 만들고, 모임 화면에서 각자 후보 시간 응답을 저장한다. 샘플 작성 시트는 Debug 캡처 전용이다. 현재 그룹 멤버 전원이 참여자로 포함되며 일부 멤버 선택은 아직 없다.

완료 기준: 새 계정은 실제 관계·기록이 생기기 전까지 빈 상태를 표시한다. Debug 화면 캡처는 샘플 데이터로 계속 가능하고 Firebase에 쓰지 않는다.

### R6. [P2] 입력 검증과 서버 규칙의 제한이 다름

근거: `PrivateCircle/MeetupFeature.swift:43`, `PrivateCircle/MeetupFeature.swift:247`, `PrivateCircle/AuthView.swift:67`, `firestore.rules:26`, `firestore.rules:57`, `firestore.rules:69`.

서버 규칙에는 이름·모임 제목 80자, 장소 100자 제한이 있지만 회원가입 및 모임 폼은 이를 검증하지 않는다. 사용자는 제출 가능한 상태에서 저장 거부를 겪게 된다. 일정 개수 제한도 현재는 주로 작성 화면에 의존한다.

수정: 공백 정리, 길이, 후보 개수, 중복·과거 시간 등 검증 기준을 정하고 화면·저장 계층·규칙을 맞춘다. 입력 문제는 해당 필드에서 설명하고, 권한 오류와 네트워크 오류를 구분한다. 문자열 길이의 Unicode 처리도 서버 기준과 일치하는지 확인한다.

진행: 가입 이름, 모임 제목·장소, 참여 인원, 후보 개수의 화면·저장 계층·Firestore 규칙 제한을 추가했다. 문자열 길이의 Unicode 처리와 규칙 Emulator 테스트는 남아 있다.

완료 기준: 제한 경계의 입력을 검증하고, 잘못된 입력을 저장하기 전에 수정할 수 있다. 직접 요청으로 화면 검증을 건너뛰어도 서버가 잘못된 데이터를 거절한다.

### R7. [P2] 모임 조회 실패 뒤 화면에서 재시도할 수 없음

근거: `PrivateCircle/ContentView.swift:119`, `PrivateCircle/MeetupFeature.swift:29`, `PrivateCircle/MeetupFeature.swift:169`, `PrivateCircle/HomeView.swift:19`.

모임 조회는 상위 탭 화면의 사용자별 작업에서 실행된다. 모임 화면에는 다시 불러오기나 당겨서 새로고침이 없고, 홈에는 모임 오류 상태가 전달되지 않는다. 첫 조회가 실패하면 홈은 데이터 없음으로 표시하고 사용자가 화면에서 조회를 재시도할 방법이 없다.

수정: 초기 로딩·빈 목록·오류·기존 데이터 갱신을 구분하고 재시도 경로를 추가한다. 공동 모임 단계에서는 필요한 화면의 변경을 구독하며, 구독 수명은 R2의 계정 경계에 맞춘다.

진행: 모임 목록·상세에 당겨서 새로고침, 빈 조회와 실패 구분, 수동 재시도를 추가했다. 홈 화면의 직접 재시도와 실시간 업데이트는 미구현이다.

완료 기준: 최초 요청 실패 후 연결이 복구되면 앱 재시작이나 재로그인 없이 복구된다. 실제 빈 목록과 조회 실패가 다른 상태로 표시된다.

## 현재 구조

```text
  PrivateCircleApp
  Firebase 초기화
  ContentView
    SessionStore -> Firebase Authentication
    UserTabs(uid별 화면 수명)
      HomeView -> MeetupStore(개인 초안 + 그룹 공동 모임)
    GroupsView -> GroupsStore -> Firestore(그룹/초대/멤버)
      GroupDetailView -> 그룹 모임 작성 + 멤버 목록
    FriendsView -> 실제 관계 연결 전 빈 상태
    MeetupsView -> MeetupStore -> Firestore(개인 초안 + 그룹 모임/응답)
    MemoriesView -> 사진·추억 저장 전 빈 상태
```

SwiftUI, NavigationStack, Form, Sheet, SF Symbols와 소규모 ObservableObject 저장소는 현재 규모에 적합하다. 그룹 생성과 초대 수락에 batch를 사용하는 방향도 유지한다. Xcode에는 앱 타깃 한 개가 있고, Swift 6 및 iOS 17 이상을 사용한다. 직접 연결한 패키지 제품은 FirebaseCore·FirebaseAuth·FirebaseFirestore이며, 잠금 파일의 Firebase 버전은 12.19.2다.

현재 개선의 중심은 파일 수나 새 프레임워크 도입이 아니라 계정별 수명 관리, 실제 관계 식별자, 공유 권한, 실패 복구다.

## 공동 모임 데이터와 남은 결정

공동 모임은 `Friend.id`와 그룹 멤버 문서 ID에 Firebase UID를 사용하고, `groups/{groupID}/meetups/{meetupID}`에 저장한다. 각 후보 시간에는 고정 ID가 있으며, 가능 응답은 `availability/{uid}` 문서에 분리한다. 미응답은 문서가 없는 상태, 제출 후 선택하지 않은 후보는 빈 목록으로 구별한다. 기존 개인 초안은 `users/{uid}/meetups`에 남긴다.

| 항목 | 결정할 방향 |
| --- | --- |
| 사람 식별자 | 실제 사용자 참조는 Firebase UID로 바꾸었다. 표시 이름과 권한 식별자의 별도 모델링은 후속 정리 대상이다. |
| 모임 소속 | 그룹 ID, 개설자 UID, 참여자 UID 목록을 저장한다. 현재 작성 화면은 그룹 전체 멤버를 참여자로 포함한다. |
| 공동 저장 경로 | `groups/{groupID}/meetups/{meetupID}`를 사용하고 그룹 멤버만 읽고 작성하도록 로컬 규칙에 추가했다. 규칙은 참여자 UID가 모두 실제 그룹 멤버인지 아직 검증하지 않는다. 현재 UI는 실제 그룹 멤버 목록만 제출하지만, 그룹 멤버 전체가 읽을 수 있는 정책과 함께 Emulator에서 검증해야 한다. |
| 후보 일정 | 생성 시 만든 고정 후보 ID와 시작 시간을 저장한다. 기존 개인 초안의 Timestamp 형식도 읽을 수 있게 했다. |
| 응답 | `availability/{uid}` 문서에서 본인 응답만 저장한다. 미응답은 문서 없음, 응답 후 미선택은 빈 후보 목록이다. 가능 수와 전원 가능 시간을 표시한다. |
| 확정 | 개설자만 후보를 확정하고 상태를 보존하는 흐름은 아직 구현되지 않았다. |
| 기존 개인 모임 | 기존 경로의 초안으로 보존한다. 공동 모임으로 옮길 때 실제 그룹·참여자를 다시 선택한다. 샘플 UUID를 실제 UID로 자동 간주하지 않는다. |
| 직렬화 | 저장 형식을 명시한 모델과 변환 코드를 분리한다. 디코딩 실패를 `compactMap`으로 조용히 숨기지 말고 진단·복구 가능하게 한다. |

참여자 일부만 선택하는 기능을 넣을 때는 그룹 멤버 전체 열람과 선택된 참여자 열람 중 제품 정책을 결정하고 규칙을 함께 좁힌다. 다른 그룹 사용자·그룹 멤버가 아닌 UID·이메일 미확인 계정은 Emulator에서 거부되는지 확인한다. 그룹 탈퇴·멤버 제외·초대 취소 시 관련 멤버십과 권한을 정리하는 규칙도 실제 사용자 테스트 전에 마련한다.

## 파일 구성 개선

기능을 수정하는 시점에 필요한 파일만 나눈다. Xcode 프로젝트의 소스 등록도 함께 갱신한다.

- `AuthView.swift`: 화면, `SessionStore`, `AppUser`를 분리한다.
- `GroupsView.swift`: 그룹 모델, `GroupsStore`, 그룹 목록·상세·작성 화면을 분리한다.
- `MeetupFeature.swift`: `MeetupStore`, 저장 모델 변환, 목록·작성·상세 화면을 분리한다.
- `ContentView.swift`: 인증 상태 전환과 탭 구성에 집중시키고 친구·추억·Debug 미리보기 화면을 분리한다.
- `HomeView.swift`: 다른 기능에서도 쓰는 아바타와 행 컴포넌트는 공용 컴포넌트 파일로 이동한다.
- `Models.swift`: 사람·모임·추억 모델의 식별자와 상태 저장값을 정리한다. 사용자에게 보이는 한국어 문구는 영속 상태값과 분리한다.

지금은 기능별 저장소와 작은 변환 계층으로 충분하다. 모든 기능에 범용 Repository나 별도 아키텍처 프레임워크를 도입하는 작업은 잡지 않는다.

## 출시 전 차단 항목

- **Firebase 규칙 배포**: 로컬 `firestore.rules`는 이메일 인증, 그룹 공동 모임, UID별 일정 응답을 포함한다. 운영 프로젝트에 아직 게시하지 않았으므로 공동 모임·응답을 실제 계정으로 쓰기 전에 Emulator 검증 후 배포해야 한다.
- **계정·개인정보**: 앱 안 계정 삭제와 데이터 삭제, 개인정보 처리방침, 보관 기간, 사진 메타데이터(EXIF/위치) 처리 및 도착 상태의 동의 범위를 정의해야 한다.
- **커뮤니티 안전**: 그룹 초대 남용 방지, 사용자 차단·신고·탈퇴, 잘못된 사진 신고/삭제 절차를 추가한다.
- **사진 백엔드**: Firebase Storage 경로별 접근 규칙, 업로드 실패·재시도, 썸네일/용량 정책, 사진 삭제 시 추억 정합성은 미구현이다.
- **알림과 운영**: APNs·알림 권한/설정, 초대와 일정 변경 알림, 오류 관측·크래시 보고·지원 연락 경로를 준비한다.
- **출시 검증**: 접근성·Dynamic Type·다크 모드·오프라인, 지원 기기·OS, TestFlight, 스크린샷·심사 설명 및 연령/개인정보 설문을 확인한다. 유료 Apple Developer 계정과 서명은 Xcode에서 별도 확인한다.

## 백엔드 선택

현재 Firebase 프로젝트에는 Authentication과 Firestore, 클라이언트 모델 및 규칙이 이미 연결되어 있다. 첨부 기획서에서 언급한 Supabase는 후보로 평가할 수 있지만, 지금 전환하면 계정·그룹·초대·규칙을 다시 옮겨야 한다. 현재 규모와 코드 상태에서는 Firebase를 유지하고 실제 2계정 흐름, 지역·비용·쿼리 요구를 측정한 뒤 재검토하는 편이 변경 위험이 낮다. Firebase/Swift SDK 버전이나 요금은 출시 직전에 공식 문서와 실제 사용량으로 다시 확인한다.

## 검증과 운영 준비

현재 앱 테스트 타깃, 규칙 테스트, Firebase Emulator 설정, 배포 설정인 `firebase.json`이 없다. 소스의 `firestore.rules`와 실제 게시된 규칙의 일치 여부도 별도로 확인해야 한다. 이전 작업 기록에는 모임 규칙 미게시가 남아 있으며, 이번 검토에서는 운영 상태를 조회하지 않았다.

수정과 함께 다음 검증을 추가한다.

1. 계정 전환 중 지연된 읽기·쓰기 완료와 로그아웃 상태 정리 테스트.
2. Auth 성공 후 프로필 저장 실패·재시도 테스트.
3. 규칙 테스트: 비로그인, 이메일 미확인, 잘못된 수신자, 확인된 수신자, 기존 멤버, 선택되지 않은 그룹 멤버, 다른 그룹 사용자.
4. 중복 초대 수락, 본인 외 응답 수정 거부, 개설자 외 확정 거부 테스트.
5. 실제 두 계정으로 초대부터 일정 확정·재로그인까지 확인.
6. 저장 실패 메시지가 작성 시트 안에서 보이는지, 연결 끊김·복구, Dynamic Type·다크 모드·가로 화면 확인.

규칙은 Emulator 검증 후 대상 Firebase 프로젝트를 확인해 게시하고, 기기에서 읽기·쓰기를 확인한다. 앱은 변경 묶음마다 Simulator 빌드를 확인한다. 다음 묶음으로 넘어가기 전에 해당 범위의 완료 기준을 확인한다.
